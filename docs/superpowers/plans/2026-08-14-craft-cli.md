# The `craft` CLI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** A command-line vocabulary over a scenario directory, such that a world can be
built end to end without hand-editing a single JSON file — and such that a claim the world
cannot support is a call that fails rather than a fault discovered later.

**Architecture:** One binary, `npm run craft -- <verb>`. Every mutating verb follows the
same shape: load the directory, mutate the artifact in memory, **check, then write** — so a
refused call leaves the scenario exactly as it was. Commands that need world knowledge
compute it from the pure generator; prose the agent still edits directly.

**Tech Stack:** TypeScript ESM, Zod for file schemas, Vitest, Biome.

## Global Constraints

- `exactOptionalPropertyTypes: true` — conditional spreads, never `undefined` assignment.
- Relative imports end in `.js`.
- `npm run check` passes at the end of every task.
- **Check before write.** A command that would produce a scenario `craft check` refuses must
  not write it. The scenario on disk is always loadable.
- **Exit codes:** 0 success, 1 refused (the scenario is fine, the request was not), 2 the
  scenario could not be read at all.
- Output is for an agent to read: one fact per line, the reason first when refusing.
- Comments explain *why*, matching the density of the surrounding code.

## File Structure

| File | Responsibility |
|---|---|
| `src/craft/args.ts` | argv → verb, positional, flags; typed readers with useful errors |
| `src/craft/workspace.ts` | Load a scenario for editing, mutate, check, write atomically |
| `src/craft/world.ts` | `new`, `reseed`, `survey`, `render` |
| `src/craft/content.ts` | `claim`, `npc`, `tree`, `place`, `terraform` |
| `src/craft/story.ts` | `phase`, `scene`, `trigger`, `beat` |
| `src/craft/check.ts` | `check`, `playtest` |
| `src/craft/play.ts` | `play --headless` |
| `src/craft/cli.ts` | The registry, dispatch, help, exit codes |
| `src/tools/craft.ts` | Entry point: `process.argv` in, `process.exit` out |

### Task 1: Argument parsing and the workspace

**Produces:**
- `parseArgs(argv): { verb: string[]; positional: string[]; flags: Map<string, string[]> }`
- `class Args` with `str`, `num`, `int`, `bool`, `point`, `list`, `oneOf`, `rest`
- `interface Workspace { artifact, dir, save(), }` and `openWorkspace(id): Workspace | undefined`
- `CraftError` carrying an exit code

Steps: write `args.test.ts` covering `--key value`, `--key=value`, repeated keys, bare
flags, a missing required option naming the option, a non-integer where an integer was
asked for, and `x,y` points. Then the implementation. Then `workspace.test.ts`: opening a
missing scenario, mutating and saving, and a save refused because the mutation broke the
scenario.

### Task 2: `new`, `reseed`, `survey`, `render`

`craft new <id> --premise "..." [--duration short] [--seed <word>] [--pack p] [--tiles t]`
creates a directory with `scenario.json`, an empty `world/`, and a `story.md` stub. It
surveys to pick bounds and a spawn, and refuses an id that is taken or not a slug.

`craft reseed <id> [--seed <word>]` picks a different world. **Refuses once anything is
claimed** — a scenario with sites written against the old seed would key to towns that do
not exist. Message says so and names what is claimed.

`craft survey <id> [--radius N]` prints the surveyed world: every settlement with its id,
position, kind, building budget, biome, distance from spawn, and likely anchors. This is
what an author reads before writing anything.

`craft render <id> --at <siteId|x,y> [--width N]` prints ASCII of the real generated ground,
so an author can *look*. Reuses `src/tools/preview.ts`'s renderer.

### Task 3: `claim` and `npc`

`craft claim <id> --site <siteId> --name "..." [--short "..."] [--kind village] --description "..."`
writes a `SiteSpec` with a settlement of the right size for the surveyed budget. Refuses a
site id the seed does not produce, or one already claimed.

`craft claim ... --structure "kind:Name"` (repeatable) names buildings.

`craft npc add <id> --site S --name "..." --role "..." --at <anchor> [--in "Building"]
[--indoors] [--glyph X] [--persona "..."] [--knows "..."]... [--live] [--like <npcId>]
[--stays]` appends to the site's roster and prints the `npcId` it was given.

- `--like` makes this person share another's tree. Stored as a `treeAlias` on the spec so a
  town can be populated without thirty written conversations.
- `--live` marks them as allowed to improvise. **Refused for anybody the arc anchors** —
  that check lives in `check.ts` and is called here too, so it fails at the call.

`craft tree <id> --npc <npcId> --init` scaffolds a minimal valid tree file for the agent to
write into: one entry node, one closing choice.

### Task 4: `place` and `terraform`

`craft place <id> --item "Name" --description "..." --site S [--in "Building"]
[--anchor container] [--requires <flag>] [--show]` — resolves the placement immediately and
**refuses if it cannot land**, naming why. Prints where it landed.

`craft place <id> --sign --site S --arm <siteId>...` puts up a signpost.
`craft place <id> --gate --site S --opens-when <flag>` bars a site's gate.

`craft terraform <id> --path <x,y> <x,y> [--width 3] [--surface path|dirt|cobble]`,
`--bridge`, `--clearing <x,y> --radius N`. Each prints the tile count and refuses an edit
that touches nothing.

### Task 5: `phase`, `scene`, `trigger`, `beat`

`craft phase add <id> --name "..." --when <flag>` appends a chapter.

Every mutating verb takes an optional `--phase <phaseId>`, which routes the change into
that chapter's diff instead of the base. That is the one idea that keeps the vocabulary from
doubling: `craft place ... --phase after-the-flood` adds to the phase's `placements.add`.

`craft scene new <id> --scene <sceneId> [--at <siteId>]` scaffolds a scene with a camera
step. `craft scene step <id> --scene S --say "actor: text"` and friends append steps —
enough to build a scene without hand-editing, since the points need world knowledge.

`craft trigger add <id> --trigger T --when <condition> --scene S | --effect <json>`.

`craft beat add <id> --beat B --site S --slot N --sets-flag F [--requires F]...
[--journal "..."] [--optional] [--quest ...]`.

### Task 6: `check`

One command, every check: the schema, `verifyArtifact`, `dirProblems`, `validateArtifact`,
`checkInvariants`, `checkCompleteness`, `journeys`/`toldWhereToGo`, and — new here —
**staging every scene against the real world**, and **the live rule**: nobody the arc
anchors may be marked `--live`.

Prints findings grouped by severity, exits 1 if any error. `--json` for a machine reader.

### Task 7: `playtest`

`craft playtest <id> [--timeout ms]` runs `walkTheStory` and reports: beats opened, beats
stuck and why, errands unfinished, people absent, hand-outs the walk needed, and whether the
story finished. Exits 1 unless it finished.

### Task 8: `play --headless`

A REPL an agent drives. Reads a command per line, prints what a player would see: the map as
ASCII, the status line, the conversation panel, the quest log on request. Commands: `n/s/e/w`,
`look`, `talk`, `1..9` (choices), `search`, `enter`, `quests`, `journal`, `inventory`,
`wait`, `where`. `--script <file>` runs a canned sequence for a test.

This is what lets a review agent *play* rather than reason about the files.

### Task 9: Per-NPC improvisation

`NpcSpec.live?: boolean`, and the runtime gate: in a world with an authored cast,
improvisation is opt-in per person; in a live or procedural world nothing changes. Story
anchors never improvise either way, as now.

### Task 10: Build the fixture by CLI alone

A test that runs the CLI end to end into a temp directory and produces a scenario that
`craft check` and `craft playtest` both pass. The proof that the vocabulary is complete.
